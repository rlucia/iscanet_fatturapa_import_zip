Iscanet - FatturaPA ZIP Import

Drop a ZIP, get one Customer Invoice or Vendor Bill per inner XML — no extra menu, no extra wizard.

Italian e-invoices arrive in batches: from the Sistema di Interscambio (SDI), from intermediaries, from accounting portals, almost always packaged as a single .zip archive. Odoo 18 natively imports a bare FatturaPA .xml through l10n_it_edi, but if you upload the ZIP that wraps them, you only get a single empty draft invoice with the archive attached. This module fills that gap.

One click, many invoices

Use the very same Upload button you already know on Customer Invoices, Vendor Bills, and the journal dashboards. If the file you drop happens to be a ZIP, this module transparently opens it, pulls each FatturaPA .xml (or signed .xml.p7m) out, and feeds them one by one to the standard Odoo importer.

You end up with one draft account.move per inner document, ready to be reviewed and posted.

Before: 1 ZIP → 1 blank invoice with the ZIP attached.

After: 1 ZIP → N properly decoded invoices or bills, partner / lines / taxes / dates already filled in by l10n_it_edi.

Customer invoice or vendor bill? The XML decides.

For each XML inside the archive, the direction is detected from the document itself by matching your company's VAT or Codice Fiscale against the CedentePrestatore (seller) and CessionarioCommittente (buyer) sections.

A single ZIP may legitimately mix both directions: each move is automatically routed to a journal whose type (sale or purchase) matches the detected direction, regardless of which journal you clicked Upload from.

The detection uses the same logic as the native l10n_it_edi import — no parallel parsing pipeline, no risk of drift between this module and the official Italian EDI implementation.

Real-world archives, handled

Signed envelopes (P7M). CAdES-signed .xml.p7m files are unwrapped on the fly using l10n_it_edi's built-in signature stripper.

Nested ZIPs. A ZIP-of-ZIPs (the typical SDI batch shape) is recursively expanded; you do not need to flatten it manually.

Mixed contents. READMEs, .DS_Store, directory entries and anything that is not an .xml or .p7m are silently skipped.

Per-file resilience. One malformed XML inside a batch does not abort the rest: each entry is imported in its own savepoint, exactly as on a stock Odoo single-file upload.

Defensive by default

Built-in tripwires against malicious or accidentally huge payloads:

  • at most 1 000 entries per archive
  • at most 200 MB total uncompressed size
  • at most 5 levels of ZIP nesting

Exceeding any of these caps stops the import with a clear user-facing error, before anything is written to the database.

The thresholds are exposed as module-level constants in models/account_journal.py; raise them in a downstream module if your batches really are that large.

Drop-in with l10n_it_edi

No new menu. The override hooks into account.journal._create_document_from_attachment: bare XMLs continue through the native flow unchanged, only ZIP-shaped uploads trigger the explosion logic.

No data model changes. There are no new tables, no new wizards, no new menu items. Uninstalling the module returns Odoo to its standard behavior with zero residue.
